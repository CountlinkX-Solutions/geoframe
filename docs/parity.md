# GeoPandas / GeoPolars (dev) / GeoFrame parity matrix

Sources: GeoPandas stable API reference (geoseries, geodataframe, io, tools, sindex, testing pages all fetched OK; the
reference index page was not needed). GeoPolars `dev` snapshot (`docs/Roadmap.md`, `docs/Tier per expression.md`,
`geopolars/geopolars/geo/*.py`, `expr/geo.py`). GeoFrame = branch `feat/io-formats` (`lib/**`, `native/geoframe_core`).

Legend: ✅ done | 🟡 partial | ❌ missing | ⛔ out of scope.
GeoPolars column: `yes` = exposed in the Python API on `dev`; `no`/`roadmap` = absent (the Roadmap lists binary predicates,
set ops, interpolate/project, line joining etc. as unchecked). GeoFrame names are `GeoFrame.GeoSeries.*` unless noted.
GeoFrame backend today: `geo` 0.33, `geoarrow-*` 0.9, `geoparquet` 0.9, `proj4rs`, `flatgeobuf`, `geozero`, `shapefile` 0.9, `rusqlite` 0.40 with bundled SQLite (the only C code, compiled by `cc`), `zip`, `geo-buf`-style buffer.
Note: GeoFrame has no GeoDataFrame-level delegation of GeoSeries methods other than area/length/bounds/centroid
(users call `GeoSeries` on `gdf.geometry`); this is counted as ✅ for the series member and noted once in section 12.

## Reference testing

Since batch V every operation GeoFrame shares with GeoPandas is checked against the real library:
`test/reference/generate.py` (dev-only; GeoPandas 1.2.0, Shapely 2.2.0, GEOS 3.14.1, pyproj 3.8.0) computes
the results for a fixed corpus and commits them as JSON in `test/reference/fixtures/`;
`test/geo_frame/reference_test.exs` compares GeoFrame with them in CI without Python (16 163 cases
across 114 operations, including sjoin, sjoin_nearest, dissolve and union_all on small frames and, since batch B,
`overlay` (all five `how`s, with and without `keep_geom_type`, on polygon, line and point frames), `clip`, `clip_by_rect`,
`explode` and `intersection_all`; since batch E also concave hull, bounding shapes, inscribed circle, Delaunay,
constrained Delaunay, Voronoi and `make_grid`; since batch I1 also `is_simple`, `normalize`, `set_precision`,
`get_precision`, `to_json` and `__geo_interface__`; since batch I2 also `offset_curve`, `snap`, `shared_paths`,
`minimum_clearance`, `minimum_clearance_line`, `polygonize` and `build_area`; since batch I3 also `is_valid_coverage`,
`invalid_coverage_edges` and `simplify_coverage`; since Z1 also `has_z`, `has_m`, `z`, `m`, `force_2d`, `force_3d` and Z/M WKB and WKT). 15 730 cases agree, 433 are documented deviations (286 of them the
null/empty class) and none is unexplained. Since batch G1 the I/O fixtures are separate: 21 small Feather, GeoParquet and Arrow
IPC files written by GeoPandas 1.2 / pyarrow 26 (`test/reference/fixtures/io/`, generated by `generate_io.py`) are read in CI by
`test/geo_frame/parity_g1_test.exs`, and `scripts/crosscheck_io.sh` (dev-only) checks the opposite direction: 25 files written
by GeoFrame read correctly in GeoPandas. Known differences
are listed in `test/reference/known_deviations.exs` and the suite asserts that each one still deviates. See
`test/reference/README.md` for the tolerances and how to regenerate. Documented deviations:

- **Null and empty inputs.** GeoFrame returns `nil` where GeoPandas returns `False`, `0`, `NaN` or an empty
  geometry (`area`, predicates, `centroid`, `envelope`, `bounds`, ...); `count_geometries` of an empty atomic
  geometry is 0 (Shapely: 1). `POINT EMPTY` cannot be stored in `geo` types.
- **Invalid input.** Predicates and `relate` on a self-intersecting bowtie polygon follow geo's relate and differ
  from GEOS in a few pairs. Valid inputs agree in every case.
- **Zero-area polygons and degenerate lines.** `is_valid` accepts a polygon whose ring is collinear (GEOS: invalid)
  and `make_valid` leaves it unchanged; `is_ring` is false for the two-point closed line `LINESTRING (1 1, 1 1)`;
  `is_valid_reason` uses geo's wording, not GEOS' text.
- **`envelope` of a horizontal/vertical line.** GeoFrame returns a line; GEOS 3.14 returns a zero-area polygon with
  repeated vertices.
- **`buffer` mitre/bevel joins** on the acute corner of a closed line differ between geo-buf and GEOS; round caps
  and joins, flat and square caps on open lines agree (area within 2 %).
- **`line_merge` of a polygon** gives an empty collection (GEOS merges its boundary).
- **Set operations.** Every point/line/polygon combination agrees with GEOS (batch B removed the 302 series
  deviations and the mixed-family `dissolve` one). Remaining: `GeometryCollection` input gives `nil` for `union`,
  `difference` and `symmetric_difference` (storage flattens nested collections). Results agree within 1e-6, not
  bit-exactly: `geo`'s boolean operations snap intersection points to an integer grid (about 1e-8 of the extent).
- **Batch E.** Sixteen documented cases, all on degenerate or tied input: the concave hull of the symmetric
  `e_ring` point set (equal edge lengths erode in another order); `minimum_rotated_rectangle` of triangles and
  symmetric shapes (several equal-area minimal rectangles); `minimum_bounding_circle` of `LINESTRING (1 1, 1 1)`
  (GEOS: `POLYGON EMPTY`); `maximum_inscribed_circle` of an invalid bowtie; vertex snapping with a `tolerance` on
  clustered input (GEOS snaps against the endpoints of the triangle edge a new vertex lands on, GeoFrame against
  every kept vertex in lexicographic order); Voronoi sides of near-cocircular rounded points. Triangle sets are
  compared exactly, falling back to "same count, same union" because cocircular points have several valid
  triangulations; `maximum_inscribed_circle` is a search, so its radius is compared within the tolerance.
- **Batch I1.** `set_precision` on an invalid multipolygon (parts that overlap or lie inside each other): GEOS keeps the
  parts it was given, GeoFrame merges parts that overlap after snapping (six documented cases; valid input agrees,
  including the half-up rounding of negative numbers). `to_json` compares as decoded JSON (key order and spacing
  are not compared); a null or empty geometry has `"bbox": null` in both.
- **Batch I2.** Fifty-eight documented cases on the new operations, all on awkward input. `offset_curve` (35): the
  outer side of a closed `LineString` with a bevel or mitre join (GEOS keeps the closing bevel or drops the two
  pieces next to the start because it reads the curve off the buffer outline, whose round caps meet there; 24 cases),
  a polygon ring that is offset exactly onto the medial axis (2), and mitre or bevel joins around segments shorter than
  the distance, where GEOS cuts against the bevel-shaped buffer and GeoFrame against the disc around each vertex (9).
  The curve is compared by length and Hausdorff distance (within 1e-6); vertices GEOS adds by simplifying its input
  are not reproduced. `snap` (21): several snap points competing for one vertex or segment, where the order GEOS
  applies them in is undocumented (the port agrees in about 99 % of random cases). `polygonize` and `build_area` (1
  each): lon/lat input whose overlapping polygons are merged with geo's overlay, which snaps to a grid of about
  1e-9 degrees. `shared_paths`, `minimum_clearance` and `minimum_clearance_line` agree everywhere except the
  null/empty class; the clearance line compares equal when only an equally close pair differs.
- **Batch I3.** Three documented cases and a handful of intended differences. `invalid_coverage_edges` over a series
  with a null row (3 cases): GeoPandas 1.2 drops the null geometry before calling GEOS and pads the result with `NaN` at
  the end, so every result after the null moves up one row; GeoFrame keeps each result in its row and gives `nil`
  for the null one. Where Shapely raises (`simplify_coverage` over a null or a non-polygon row) GeoFrame returns
  `nil` for that row and simplifies the rest; `is_valid_coverage` and `invalid_coverage_edges` ignore non-polygons as
  Shapely does. A non-finite `gap_width` or `tolerance` is an `ArgumentError` (Shapely accepts `NaN` and `inf` silently), a
  row with a `NaN` or infinite coordinate is `nil`, and the work is capped (see the README limits). `simplify_coverage` and
  the validators were reconstructed from the published GEOS/JTS behaviour and then fitted to Shapely by black-box
  fuzzing (the `gap_width` rule, the vertex-in-neighbour test, the way a ring is rebuilt from its edges: the first
  edge as stored, so a ring may start at another node and come out reversed): 8,900 random validator cases,
  10,800 random coverages, 280 hand-built ones and 12,402 overlapping inputs agree vertex for vertex, as do the 805
  committed fixture cases. Structures the generators do not make (for instance one free ring shared by three levels
  of nesting) are untested.
- **Tolerances.** `to_crs` against PROJ: within 1e-6 projected units (1e-9 degrees back), including the Florida
  East (ftUS) transverse Mercator. Geodesic area, length and point distance: within 1e-6 of `pyproj.Geod`.

Fixed thanks to the suite: `distance`/`dwithin` returned `0.0`/`true` (or `f64::MAX` for an empty collection) for
empty inputs instead of `nil`; `remove_repeated_points` reduced a collapsed line to a one-point `LINESTRING`
(GEOS keeps two points).

## Batch G - I/O breadth (high value for adoption, hard)
- G1 status: done (issue #48). Arrow/Feather IO, GeoParquet write options and `bbox:` reads. - G2 status: done (issue #51). `read_postgis`/`to_postgis`, EWKB in `GeoSeries.from_wkb`/`to_wkb(srid:)` (Rust: SRID and Z/M flags are rewritten to and from ISO WKB). `postgrex` is an optional dependency; `GeoFrame.Postgrex.Extension` / `GeoFrame.Postgrex.Types` decode a `geometry` column to its raw EWKB binary (text transfer format, because the binary `geometry_send` drops the SRID); bytea and hex text are detected without the extension. Tests tagged `:postgis` run when `GEOFRAME_POSTGIS_URL` is set (CI service container); `scripts/crosscheck_postgis.sh` (dev-only) round-trips tables with GeoPandas 1.2 in both directions.
- G3 status: done (issue #53). `read_shapefile`/`write_shapefile` (+ zip), `read_gpkg`/`write_gpkg`, `list_layers`, `read_file_info`, and `.shp`/`.zip`/`.gpkg` in `read_file`/`write_file`. Not done: Z/M, memo and non-text dBase types, datetime types in Shapefile (stored as text), GeoPackage tiles/rasters/non-rtree extensions, `fid_as_index`, `where`/`bbox` filters on read, `columns`/`rows` selection. `scripts/crosscheck_io.sh` reads 23 more GeoFrame-written files in GeoPandas 1.2 / pyogrio (Shapefile, zip, GeoPackage incl. a rtree-backed bbox read), and 8 GeoPandas-written datasets (`test/reference/fixtures/io/vector/`: 5 Shapefiles incl. a zip, 2 GeoPackages with 3 layers) are read in CI.

## Z and M
- Z1 status: done (issue #74, see `odd/tasks/zm-support.md`). Storage already held XYZ, XYM and XYZM (the GeoArrow `geometry` union is dimension-aware); Z1 adds the API on top: `has_z`, `has_m`, `z`/`get_z`, `m`/`get_m`, `force_2d`, `force_3d` (Rust `zm.rs`: the dimension is read from the stored scalars, and forcing rewrites each geometry's ISO WKB, so every other ordinate is kept bit for bit). 360 reference cases (`zm.json`: points, lines, polygons with a hole, multi geometries, collections, empties of every dimension; 322 agree, 38 are the documented deviations below) compare with GeoPandas 1.2 / Shapely 2.2.
- Round trips that keep Z and M today (tested in `zm_tests.rs` and `zm_test.exs`): WKB (ISO), WKT (`POINT Z`, `POINT M`, `POINT ZM`), EWKB (PostGIS flags), GeoParquet (WKB), Arrow IPC (WKB and native point encodings), GeoPackage, `take`, `concat`, `fill_null`.
- Deviations: (1) a `GEOMETRYCOLLECTION` whose members have different dimensions is an error (the GeoArrow builder cannot store it; it used to panic inside the builder); (2) a one-member collection is stored as its member (existing behaviour), so `z`, `force_*`, `to_wkb` and `to_wkt` describe the member; (3) `force_3d` of an XYZM geometry keeps the Z and drops M, where Shapely 2.2 drops M and overwrites Z with the fill value; (4) an empty multi geometry or collection keeps its declared dimension (`MULTIPOINT Z EMPTY`), where Shapely discards it (part of the null/empty class).
- Still 2D: every operation that goes through `geo` types (the geo bridge: `geo_rows`, `rebuild`, `map_geometry`), `from_xy(z:)`, `get_coordinates` and the GeoJSON, FlatGeobuf and Shapefile readers and writers; the GeoPackage `z`/`m` contents flags and GeoParquet `geometry_types` (` Z`) are not written either. Tracked as Z2 to Z5 in `odd/tasks/zm-support.md`.
